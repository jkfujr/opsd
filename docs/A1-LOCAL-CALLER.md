## 1. 范围

**保留**：`/run/opsd` 目录 `0750`、socket `0660`（`root:opsd`）继续作为第一道门槛，决定哪些进程能连上。

**新增**：接受连接后读取对端凭据，只放行节点服务账号。两者是叠加关系，不是替换——权限位仍然生效，A1 只在其后追加身份判定。

**不做**：A1 不判断"这个调用方可以执行哪些操作"（那是 A2），也不处理远端请求授权（A3/A4）。

**只包在 `serveExecutor` 的监听上**：节点自己的控制 socket（`cli/node.go:160`）不套这层校验。

**已存在的相邻通道**：同一进程还另起一个节点控制 socket（`/run/opsd-node/control.sock`，`cli/node.go:160`），权限 `0600`，所在目录 `RuntimeDirectoryMode=0700`。CLI 的 `data`／`operation` 等命令连的是它（`cli/data.go:40`、`cli/node.go:399`），由节点处理后再转执行器。也就是说 **root 无需直连执行器 socket**——这条通道已经只允许属主，A1 不去改动它。它也是"权限位 + 目录模式"足够用的先例。

## 2. 机制

Linux 上用 `SO_PEERCRED` 取对端身份：

```go
ucred, err := unix.GetsockoptUcred(conn, unix.SOL_SOCKET, unix.SO_PEERCRED)
// ucred.Uid、ucred.Gid、ucred.Pid
```

它是内核在连接建立时记录的凭据，调用方无法伪造（与 `/proc` 自查相比不依赖时序）。因此：

- 在 `Accept` 之后、读取请求之前取凭据；
- UID 不在允许集合内 → 立即关闭连接并记日志（含 uid/gid/pid 与拒绝原因），**不读取任何请求体**。

## 3. 允许哪些 UID

| 调用方 | 是否放行 | 依据 |
|---|---|---|
| 节点服务账号（`opsd`） | ✅ | `cli/node.go:79` 的 `serveNode` 是唯一构造执行器客户端的路径，且它显式拒绝以 root 运行（`node.go:80-81`） |
| 同组其他 UID | ❌ | 这正是 A1 要拦的：目前它们打开 0660 socket 即可驱动 root |
| root | ❌ 默认拒绝 | root 在文件权限层面本可绕过 socket 模式，但 `serveNode` 不接受 root 运行，因此 root 不是合法调用方；排障确需时另开显式开关，不默认放行 |

**允许集合只含一个 UID**，不做"组"级别的放行——按组放行等于把 A1 退回现状。

## 4. 允许的 UID 从哪来

安装器已经在 `installation/node.go:71-81` 用 `user.Lookup("opsd")` 得到 `uid`，但 `NodeFile` 只持久化了 `GroupID`（`node.go:25`）。A1 需要补一个字段：

```go
type NodeFile struct {
	...
	GroupID int `json:"group_id"`
	UserID  int `json:"user_id"`   // 新增
}
```

`user_id` 必须是**指针类型**（`*int`），否则无法区分"旧配置缺字段"和"显式写了 0"：

- **全新安装**：安装器把已有的 `uid` 直接写入 `user_id`，不需要新查询；
- **显式 0**：视为非法配置，监听前报错，不做兜底查询。
- **升级已有安装**：旧 `node.json` 没有 `user_id`，值为 0。此时执行器启动阶段自行解析：
  1. `user.Lookup("opsd")` 成功 → 使用其 UID 并记一条"由服务账号名推导"的日志；
  2. 查询失败 → **拒绝启动**并给出明确错误，不降级为"不校验"。
- 执行器以 root 运行，`user.Lookup` 一定可用；失败只可能是服务账号缺失，这种情况继续运行没有意义。
- **现有 Linux 集成测试以 `nobody` 启动节点**（`cli/node_linux_test.go:122`），其配置须显式写入 `65534`，不能依赖名称推导。

信任前提：允许 UID 来自配置文件，而配置（生产路径 `/etc/opsd/instance.json`）由安装器以 `root:opsd`、`0640` 写入，只有受信任的管理员能改。A1 不校验配置文件本身的完整性。

## 5. 读取凭据失败怎么办

**一律拒绝（fail closed），但只拒绝这一条连接**：

- socket 来自非 Unix 通道、`GetsockoptUcred` 返回错误、或返回全零 UID → 关闭连接、记日志；
- **不能把拒绝当成 `Accept` 的错误返回**：`http.Server.Serve` 收到 `Accept` 错误会终止整个服务，必须关闭该连接后继续接受下一个；
- 不提供"读不到就放行"的分支，也不提供环境变量绕过。

非 Linux 平台没有 `SO_PEERCRED`（`LOCAL_PEERCRED` 语义不同）。部署目标只有 Linux（systemd 单元），因此：

- 凭据读取用 `//go:build linux` 实现；
- 其他平台**拒绝启动执行器监听**并提示平台不支持；
- 若 Windows 本地测试需要起监听，用显式编译期开关（测试专用 tag），不使用运行期环境变量，避免生产误开。

## 6. 滚动升级与兼容性

| 组合 | 行为 |
|---|---|
| 新节点 ↔ 新执行器 | 校验生效，节点账号放行 |
| 旧节点 ↔ 新执行器 | 旧节点也是 `opsd` 账号，UID 相同 → 不受影响 |
| 新节点 ↔ 旧执行器 | 旧执行器不校验，行为同现状 |

因此不需要协议版本协商，也不需要停机窗口：升级执行器即生效，节点侧无改动。

## 7. 验收

1. **正常调用**：以节点服务账号启动节点，执行一次需要 root 的操作（如查看执行器状态 / 触发一次受管操作），成功。
6. **拒绝后服务仍存活**：先制造一次被拒连接，随后合法 RPC 仍成功——证明拒绝没有把 `Serve` 打停。
2. **同组其他 UID 被拒**：以组 `opsd` 内的另一个 UID（测试用临时账号，或测试进程 `setuid` 到该组的其他 uid）连接 socket，连接被立即关闭，执行器日志记录拒绝原因，且该请求未被执行。
3. **升级后仍可用**：用不含 `user_id` 的旧 `node.json` 启动新执行器，节点服务账号调用成功，日志显示由服务账号名推导。
4. **凭据读取失败被拒**：构造非 Unix 对端或注入读取失败，连接被拒绝，且没有请求被执行。
5. **无回退路径**：确认代码中不存在"读不到凭据就放行"的分支。

第 2 项需要 Linux 环境（本地 WSL 缺网络但可用现有发行版；GitHub runner 也可）。若用测试进程切换 UID，需要 root，测试标记为需要 `OPSD_*` 显式开关，不能拖慢默认 `npm test`。

## 8. 已知限制

- **同 UID 进程共享准入**：任何以 `opsd` 身份运行的进程都通过 A1。A1 只区分"是不是节点账号"，不区分"是不是节点本进程"。要区分需要再加进程级凭据（如 SO_PEERCRED 的 `Pid` 与 systemd `MainPID` 比对），但那会在节点重启竞态期引入误拒，建议放到 A2 之后单独评估。
- **PID 复用**：`ucred.Pid` 只用于日志与将来的比对，不作为准入依据。

## 9. 评审结论（2026-11-23）

三点均按设计通过，另加两条强制要求：

- 默认拒绝 UID 0：仓库内业务客户端只由普通用户节点创建；root 的恢复与独立操作服务直接打开执行器数据库，管理 CLI 走节点 `control.sock`；现存 root 连执行器 socket 的代码只做存活探测。**不加 root 放行开关**。
- `user_id` 放现有 `NodeFile`（生产路径 `/etc/opsd/instance.json`，安装器以 `root:opsd`、`0640` 写入，两个服务已共读）。
- 接受"同 UID 进程共享准入"：`Pid`/`Gid` 只用于日志，`MainPID` 比对留待后续评估。
- 强制：校验只包 `serveExecutor` 监听；单条连接被拒时关闭并继续 `Accept`。
- 升级无需协议协商；现有更新流程会重启服务，活动终端断开属于预期。
