## 1. 现行行为

### 1.1 进程与身份

安装器生成的两个常驻单元权限差异是整套边界的基础（`backend/internal/installation/node.go:176-177`）：

| 单元 | 运行身份 | 组 | 运行目录与掩码 |
|---|---|---|---|
| `opsd.service`（对等节点） | `User=opsd` | `Group=opsd` | `RuntimeDirectory=opsd-node`、`RuntimeDirectoryMode=0700`、`UMask=0077` |
| `opsd-executor.service`（本机执行器） | **`User=root`** | `Group=opsd` | `RuntimeDirectory=opsd`、`RuntimeDirectoryMode=0750`、`UMask=0007` |

节点单元另外声明 `NoNewPrivileges=true`、`ProtectSystem=strict`，并以 `ReadWritePaths` 限定可写目录。

### 1.2 执行器的准入条件

执行器**只经本地 Unix Socket 接受有类型的请求**（`backend/internal/executor/local.go:1`），不监听网络端口。路径与权限：

- socket 路径 `/run/opsd/executor.sock`（`installation/node.go:84`）；
- 监听后立即 `os.Chmod(socket, 0660)`（`executor/local.go:207`）。

因此在现行实现中，**执行器的准入等价于"该进程能否打开这个 socket"**：属主是 root，组是 `opsd`，组内任何进程都可写。执行器自身不再核对调用方身份。

> 风险含义：`opsd` 组内的任何进程都能驱动以 root 身份运行的执行器。节点进程失陷、或任何以 `opsd` 组身份运行的程序被利用，都等价于获得执行器的能力。这正是方案 A2–A4 要处理的范围。

### 1.3 节点之间的终端通道

远端终端不是"入口放行即可用"。发起方先取目标节点的成员记录（`cluster/terminal.go:28` 调用 `n.Member(ctx, target)`），建立隧道后再校验对端自报的成员数据（`cluster/terminal.go:64`）：

- `remote.ID` 必须等于目标节点；
- `remote.Public` 必须与已知成员公钥一致；
- `remote.Cluster` 必须与本集群一致；
- 通过 `validateMember` 的结构校验。

即**目标节点按自己的成员名单与撤销状态授权**，不依赖发起方的声明。

### 1.4 管理员会话

控制台管理员会话在入口处校验（登录、会话 cookie、CSRF）。授权信息随会话带入，跨节点调用时由目标节点复核成员身份（见 1.3）。

### 1.5 数据归属

各类数据的权威来源、写入方与副本用途统一记录在
[架构](ARCHITECTURE.md#数据类型与权威来源)，本文档不重复列举，避免两处漂移。

---|---|---|
| 集群共享状态（节点、任务、操作、主题、账号等） | **共享 SQL**（`backend/internal/sharedsql`，迁移在 `backend/internal/storage/migrations/`） | 共享库可用时以它为准；节点不各自保存副本。 |
| 节点私有状态（本机配置、凭据缓存、本地队列） | **本机目录** `localstate` / `/var/lib/opsd/node`、`/var/lib/opsd/executor` | 不参与跨节点一致性，节点重建后允许丢失。 |
| 监控归档 | **S3 对象存储** | 由采集侧写入、查询侧只读；保留与降采样由 Compactor 执行。 |
| 前端与主题产物 | 构建产物（`webassets` 内嵌 + 外部主题 ZIP） | 只读，不构成数据权威。 |

写入方约束：共享库的写入只发生在控制面与节点模块内，迁移文件是唯一的结构来源；节点私有目录只由该节点自身写入。

## 2. A0 待决问题

本节**不是承诺**，而是 A0 起需要先定方向的问题。任何一项落地前都需要设计文档与验收。

1. **执行器不再"信任 socket 打开者"**（方案 A2–A4）：改为显式授权——按调用方凭据、被允许的操作类型与资源范围判定，而不是依赖文件权限。目标是在节点进程失陷时限制可造成的后果。
2. **root 终端默认关闭**（方案 A0）：默认关闭会改变现有可用功能，因此必须先定义新旧节点共存时的行为，再分批实施；本文档不定时间表。
3. **节点进程失陷后的爆炸半径**：当前执行器与节点共享 `opsd` 组，边界只有 socket 权限。目标方向是缩小执行器暴露的操作集合，并让高风险操作需要额外凭据。
4. **数据权威的收敛**（方案 D）：共享库与本地状态之间的写入路径需要显式枚举，避免同一事实两处可写。当前仅记录"谁是权威"，尚未做写入路径枚举。
5. **审计**：现行实现记录 HTTP 请求日志与操作记录，但没有独立的"谁在何时授权了什么"的审计流。是否需要单列，待定。

## 3. 维护约定

- 改动 1.1–1.4 描述的行为时，**必须同步更新本文档**；只改 1.1 的单元权限而不更新这里，视为缺陷。
- 新增数据类型时，必须在 [架构](ARCHITECTURE.md#数据类型与权威来源) 的表格里登记权威来源与写入方。
- 依赖方向的固化由测试承担（`backend/internal/architecture/layers_test.go`），不在本文档重复列举。
